## D1-D6 决策锁

- **D1 分层架构 (回答用户'高度疑问才人审')**: 两层两种门。
  - 层 1 知识图谱/DB 层 (Phase 16/17 已造): 机器可写、可逆、带 provenance — 归一层三出口 AUTO/REVIEW/NEW, REVIEW 进复核篮子。**AUTO 零疑问项直接入图谱, 不设人审**。
  - 层 2 OKF 官方档案层 (本阶段): 机器永远走 提案→人审→合入; 自动合入代码**不实现** (T8 红线: 连 off 状态都不做)。
  - 理由: 图谱是派生索引 (可重建), OKF bundle 是 SSOT 官方档案 (升级即定案) — 风险等级不同, 门也不同。
- **D2 提案准入分级**: 上游预筛决定什么值得成为提案 — 抽取层 REVIEW 出口项 + 跨文档合并建议 + 新知识主张 → 提案; AUTO 出口项留在图谱层 (可通过批量摘要提案让人一键知情, 不逐条审)。
- **D3 提案格式**: 一提案一 JSON 文件 (llm-wiki-compiler 蓝本翻译 Python): target_file + diff/新内容 + reason + evidence(span_id 溯源) + proposed_by + created_at; **无 span_id 的提案允许进 staging 但标 unverified** (boundary OQ1 官方倾向)。
- **D4 审计 journal 放 OKF bundle 内** (文件, 随知识包走; DB 只是缓存 — boundary OQ2 官方倾向); 每条含 approvedBy/approvedAt/rejectedReason 显式审计字段 (增补蓝本缺失)。
- **D5 并发策略**: 先到先审; 合入后其余对同一目标文件的提案强制 rebase 重审 (boundary OQ3 官方倾向)。
- **D6 人审界面**: CLI (list/show/approve/reject/merge), 不做 Web UI; 展示 diff 非全文 (防橡皮图章)。

## 红线 (从 18-BOUNDARY.md 逐字继承)
1. 自动 commit/自动合入代码不存在 (T8; 未来需单独授权+质量门)。
2. raw/ 与 sidecar 零回写 (机器区只能由 serializer 重建); 合入执行器可写路径白名单 = entities/concepts/synthesis。
3. git 操作永远人做 (提案合入只改工作区文件)。
4. 提案质量自动评分不做 (Phase 19 评估域)。
5. 全程约束: 禁网络模型下载/RaNER 推理/live gate 逐门授权/C2/commit/push; 单实现 writer + 非实现协调器; claims untrusted。
