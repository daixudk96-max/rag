## 1. Verdict
- NO single open-source project covers our full cross-document entity normalization chain. Ecosystem = 3 blocks: (A) record-linkage tools (blocking/scoring/active learning), (B) NEL systems (mention -> fixed encyclopedia KB), (D) RAG/KG frameworks (mostly exact-name key merging, NOT real identity resolution).
- LightRAG maintainers CONFIRMED: base entity merge relies on exact name matching; semantic candidates + LLM validation were a suggested enhancement (2025 issue: "solely based on exact name matches", suggested vector candidates + cosine ~0.8 + top-k 10 + LLM validation), not default ingestion ER.
- Our problem is ONLINE/INCREMENTAL entity resolution ("new mention -> existing canonical entity? with what evidence? create new?"), NOT encyclopedia linking. This reframing is load-bearing.

## 3. A-class: adapt "row records" to "entity evidence"
- Pair feature vector: name_exact_normalized / name_suffix_removed_equal / alias_table_hit / char_similarity / traditional_simplified_equal / english_name_equal / legal_id_equal / legal_id_conflict / legal_representative_equal / registered_address_overlap / same_product_or_parent_context / cooccurring_entities_overlap / embedding_cosine / source_reliability. Output: pair_score + decision AUTO_MERGE|REVIEW|NEW_ENTITY + evidence_json + model_version.
- Splink ranking for us: Splink scoring idea > dedupe active-learning loop > Zingg architecture > recordlinkage API skeleton > py_entitymatching/FEBRL.
- dedupe loop to copy (not necessarily the lib): 机器高置信->AUTO_MERGE; 低置信->separate/NEW; 中间->review_queue -> 人标 same/different -> 累积 hard examples -> 周期性校准 scorer. SAVE NEGATIVE LABELS: 华为技术有限公司 != 华为数字能源技术有限公司 hard negatives > 1000th positive alias. gold_pairs_positive/negative = long-term moat.
- Zingg: blocking model and similarity model must be SEPARATE (never share one threshold between candidate generation and final decision). Spark/JVM + AGPL = too heavy for us.

## 4. NEL lessons (architecture only, not production deps)
- BLINK two-stage (dense retrieve -> expensive rerank) translates to: mention -> rule blocking (normalized_name/alias index/char trigram/type) + pgvector ANN -> top-10 candidates -> feature scorer/cross-encoder/LLM judge -> merge/review/create. NOT "cosine>0.85 -> merge" (would crush 华为技术/华为终端/华为数字能源/华为云计算 into one cluster).
- GENRE constrained decoding -> LLM judge prompt pattern: given mention+context+7 candidates, output ONLY candidate_id or NONE + evidence fields + contradictions + confidence. LLM never creates canonical entities. (GENRE itself CC-BY-NC - idea only.)
- Chinese NEL ecosystem genuinely thin + academic licenses (CCKS 2019 non-commercial; DuEL KB incomplete). CN-DBpedia: no maintained official repo with clear commercial dump license - "可访问"与"可商业复制"是两回事.

## 6. Load-bearing architecture rule
**PostgreSQL canonical tables = SOURCE OF TRUTH; graph/vector indexes are DERIVED and must be rebuildable. Never the reverse.** (LightRAG docs admit graph/vector drift; they provide rebuild-from-source tooling - direction confirmed.)

## 7. RapidFuzz hot path + normalization discipline
- Pipeline: mention_norm -> PG exact/alias lookup -> pg_trgm/prefix blocker (~500 cands) -> RapidFuzz (top 20) -> structured scorer (top 3) -> LLM/human when needed. Compare only blocker candidates, never full-table.
- Normalize variants: norm_full / legal_suffix_removed (华为技术有限公司->华为技术) / region-aware variants; compute MULTIPLE independent features (exact_full, exact_suffix_stripped, levenshtein_ratio, jaro_winkler, lcs, char_bigram_jaccard, prefix_containment, alias_dictionary_hit) not one ratio.
- Pinyin: recall-only weak feature (张伟/章伟/张威 collide), NEVER merge evidence.
- Suffix removal: candidate generation ONLY; 集团/股份 suffixes carry legal boundaries; always keep raw_name + normalized_full_name + search_variant_name (no destructive normalization).

## 8. Authority anchors (hard evidence)
- USCC 统一社会信用代码 (GB 32100-2015, 18位): same valid USCC -> strongest positive (usually auto same LEGAL entity); different valid USCC -> HARD NEGATIVE, must not merge as legal entity.
- Legal entity != group: 华为技术有限公司/华为终端有限公司/华为数字能源技术有限公司 = separate ENTITY nodes + SUBSIDIARY_OF/BRAND_OF/AFFILIATED_WITH relations. Never merge group into identity cluster.
- GLEIF: search API, fuzzy name/address matching, ownership, BIC/ISIN mappings. OpenCorporates: ODbL share-alike caution; copy (jurisdiction, registration number) + provenance pattern.
- 企查查/天眼查/爱企查: contract-bounded verification/enrichment ONLY; cache per contract; save provider+timestamp+external_id; never bulk-scrape into alias table (future tech debt = unprovable alias provenance/license).
- Canonical entity_id = OUR permanent UUID; LEI/USCC/Wikidata QID/OpenCorporates ID = external identities in entity_identity_key, never the primary key.
- alias table schema requires provenance: alias_id, entity_id, alias_text, alias_norm, source_type, source_uri, source_record_id, license_tag, discovered_at, valid_from, valid_to, confidence, approval_status.
