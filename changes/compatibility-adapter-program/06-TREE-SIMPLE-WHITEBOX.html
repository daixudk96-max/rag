树流程超白话版

一句话：系统先把文档切成很多小纸条，再把这些小纸条试着分组，做成一棵树。
现在的默认树 能用，但对“结构很乱的文档”不够聪明。
如果接入 donor（比如 PageIndex），树可能会更像人类看到的目录树，但通常更依赖 LLM。

1. 现在系统是怎么做树的？

第 1 步

把文档切成很多小纸条。

每张小纸条里有一句或一小段话。

→

第 2 步

看看这些小纸条有没有“标题线索”。

比如 heading、层级、位置。

→

第 3 步

把差不多的一组纸条放到同一个小盒子里。

这个“小盒子”就是一个树节点。

→

第 4 步

给每个盒子再算一份“语义画像”。

也就是：这组内容大概在讲什么。

2. 不用 LLM，会不会完全不能用？

不会完全不能用。

当前默认树，不用 LLM 也能跑。

它主要靠：

  • 文档被切出来的小纸条
  • 这些纸条的位置关系
  • 标题/层级线索
  • 简单的向量统计

所以它不是“坏掉”，而是：

  • 对结构清楚的文档：够用
  • 对讲话稿、流水文、弱结构文档：容易长得比较粗糙

3. 那它现在到底是按什么来分树？

不是直接按 Markdown 文件硬切。

更准确地说：

  1. 先把 PDF / DOCX 解析成很多 span（小纸条）
  2. span 里会带一些结构线索，比如 heading_path
  3. 树生成器主要按这些结构线索分组
  4. 再加一点点语义聚合，把很像的内容放近一点

所以它更像：

先看结构
再补一点语义

而不是：

完全靠 LLM 理解全文后再建树

4. LLM 在树里现在起什么作用？

当前默认主线里，LLM 不是必须的。

但如果你想要 donor（比如 PageIndex）做更像“目录树”的结构抽取，LLM 通常会有帮助。

简单说：

  • 默认 baseline：不用 LLM 也能建树
  • donor 的结构增强：通常更依赖 LLM

5. 当前主线 vs donor 路线

当前默认主线

本地树生成

本地向量统计

本地下钻决策

稳定、可追溯

vs

donor 路线

更强的树结构逻辑

更强的目录/层级理解

更强的分支决策

但更依赖 LLM 或 donor 自身逻辑

6. 你现在最该记住的一句话

不用 LLM，树不是不能用；只是更容易“分得粗”。
用 LLM 或 donor，树可能更像人类理解的目录树；但复杂度和依赖也会更高。
